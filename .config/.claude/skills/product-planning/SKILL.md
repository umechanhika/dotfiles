# 企画・改善案の検討

新機能の提案、既存プロダクトの改善、施策の立案など、「何を作るか」を決める作業に適用する。

### 問題の在りかを先に特定する

- 要望を実装する前に、それが機能不足なのか、プロダクトの構造そのものの限界なのかを判定する。
- 構造の限界なら機能を足しても解消しないため、作り替えを選択肢に含める。
- 判定は数値で行う。到達しうる上限、最適に近い解の性能、習熟に要する時間などを測り、上限が近いなら機能追加は効かないと結論する。
- 利用者の声は要望リストではなく症状として読み、その不満を書かせた原因を特定する。
- 同じ不満が競合や類似プロダクトにも出ているなら、個別の作り込み不足ではなく構造が原因である裏付けとして扱う。

### 根拠の質を明記する

- 施策の根拠には、実証研究・相関・経験則のどれに依拠しているかを併記する。
- 「何を作るか」は経験則に依拠してよいが、「どう使い続けさせるか」は実証研究に依拠する。
- 確認済みの事実と自分の推測を必ず分けて書き、事実には出典を付ける。

### 判断を検査可能な形にする

- 調整可能なパラメータを含む案は、受け入れ範囲を先に決め、実測値がその範囲に入るまで調整してから提示する。「たぶん良い」で出さない。
- 面白いが突出する案は意図的に捨てる。突出した選択肢は「常にそれを選ぶのが最適」を生み、他の選択肢を殺すため。
- プロダクトごとに「これが破れたら存在意義が消える」不変条件を 1 行で言語化する。
- 受け入れ範囲と不変条件は、レビューではなく自動テストで固定する。作り手は前提を知っているため、目視では破りに気付けない。
